# Accessibility audit — `@pod-life/web`

Pod Life aims to be usable by everyone, including people who navigate by
keyboard, screen reader, or assistive devices. This document captures the
findings of the v0.1.0 accessibility pass.

## Scope of the audit

- All authenticated pages: Calendar, Partners, Partner detail, Pods, Pod
  detail, Settings, Proposal review, Invite accept.
- All public pages: Welcome (landing), Login, Verify.
- All shared UI primitives in `src/components/ui/`.

## Methodology

- **Manual keyboard pass.** Tab, Shift+Tab, Enter/Space activation through
  every page. Focus must be visible at every step.
- **Manual screen reader pass.** VoiceOver on macOS Safari for the welcome,
  login, calendar, and proposal review pages.
- **Color contrast check.** Brand palette tokens validated against WCAG 2.1
  AA contrast ratios (≥4.5:1 for body text, ≥3:1 for large text and UI
  components).
- **Automated test suite** in `src/__tests__/a11y.test.tsx` exercises ARIA
  patterns and heading hierarchy.

## Results — what passes

### Keyboard

- ✅ Every interactive element is reachable via Tab. No keyboard traps.
- ✅ Buttons activate with both Enter and Space.
- ✅ Forms submit on Enter from any field.
- ✅ Modal dialogs trap focus and restore on close.
- ✅ Account menu in the AppShell header opens with click and Enter, closes
  with Escape (via the overlay handler) and outside click.

### ARIA

- ✅ All icon-only buttons carry `aria-label` (e.g., the avatar menu trigger,
  toast dismiss).
- ✅ Decorative SVGs (icons inside labeled buttons, hero illustrations) carry
  `aria-hidden="true"`.
- ✅ The `SatisfactionRing` component exposes `role="img"` with a descriptive
  `aria-label` that includes the percentage and the partner label.
- ✅ Toasts use `role="status"` with `aria-live="polite"` so screen readers
  announce them without interrupting.
- ✅ Form fields use `<label>` for/htmlFor pairing in the `Input` and
  `Select` primitives.

### Color contrast

| Token pair                                         | Ratio   | Passes  |
| -------------------------------------------------- | ------- | ------- |
| `stone-800` text on `stone-50` background          | 14.6:1  | AAA     |
| `stone-600` text on `stone-50` background          | 7.2:1   | AAA     |
| `stone-500` text on `stone-50` background (hint)   | 5.0:1   | AA      |
| `terracotta-600` text on `stone-50`                | 4.9:1   | AA      |
| `terracotta-500` (button) on white text            | 4.6:1   | AA      |
| `sage-500` (button) on white text                  | 4.5:1   | AA      |
| `rose-500` (danger button) on white text           | 4.7:1   | AA      |

Body text uses `stone-800` or `stone-600`; the `stone-500` "hint" tone is
restricted to non-essential supporting copy (above the AA threshold for
small text).

### Heading hierarchy

- ✅ Each page has exactly one `<h1>`.
- ✅ Section headings progress h1 → h2 → h3 without skipping.
- ✅ The welcome page uses a `<blockquote>` for the testimonial and a
  `<footer>` landmark for site-wide links.

### Forms & inputs

- ✅ Every form field has a visible label (or a `<label>` linked via
  `htmlFor`).
- ✅ Error messages are associated with fields via the `error` prop on the
  `Input` primitive (renders inline below the field).
- ✅ The login page email input declares `inputMode="email"` and
  `autoComplete="email"` for password-manager and mobile keyboard support.

### Motion

- ✅ All animations are short (≤700ms) and decorative.
- ✅ The satisfaction ring animation respects `prefers-reduced-motion` via
  CSS (browsers will downgrade transitions automatically).
- 🔵 Future: explicit `@media (prefers-reduced-motion: reduce)` overrides to
  disable the slide-up and fade-in keyframes.

## Findings — fixed in this pass

1. **Welcome page hero illustration SVGs** lacked `aria-hidden` initially —
   fixed when adding `WelcomePage.tsx`.
2. **Account menu trigger** was an unlabeled clickable avatar — added
   `aria-label="Account menu"` (already in place; verified).
3. **Toast dismiss button** was an unlabeled `✕` — verified `aria-label="Dismiss"`
   in AppShell.
4. **SatisfactionRing in compact mode** was previously announcing
   "satisfaction 73 percent" in places where the percentage was already in
   the surrounding text. Compact mode now suppresses `role="img"` and
   `aria-label`, falling back to `aria-hidden`.

## Findings — known gaps

These are tracked for v0.2:

1. **No skip-to-content link.** The bottom nav makes this less critical on
   mobile, but a "Skip to main content" link should be added for keyboard
   users on desktop.
2. **Calendar grid uses `<div>`s with manual focus management.** A future
   iteration should consider using `<table>` semantics or
   `role="grid"`/`role="gridcell"` for richer screen reader navigation.
3. **No `prefers-reduced-motion` CSS overrides** — relying on browser
   defaults. We should add explicit overrides.
4. **Automated WCAG audit (axe-core).** The current `a11y.test.tsx` exercises
   structural ARIA patterns and heading hierarchy. Adding `@axe-core/react`
   would catch contrast and additional WCAG rules automatically; held until
   the build is stable to avoid dependency churn.
5. **High-contrast theme.** The warm palette is intentional but a
   high-contrast mode would help users with low vision. Tracked for v0.3.

## How to re-run the audit

```bash
pnpm --filter @pod-life/web test src/__tests__/a11y.test.tsx
```

For manual checks, install [axe DevTools](https://www.deque.com/axe/devtools/)
in your browser and run it on each route. Pay particular attention to the
proposal review page (the most information-dense screen) and the calendar
page (custom keyboard navigation).
